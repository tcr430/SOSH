# ADR 0001 — Database Schema (Phase 1 MVP)

**Status:** Accepted
**Date:** 2026-04-30
**Phase:** 1 — MVP
**Scope:** Complete Supabase schema for Phase 1 (signup → onboard → connect → campaign → generate → approve → publish), including engagement inbox, AI usage tracking, Vault-stored tokens, RLS, indexes, triggers, and migration order.

---

## Goals

This document is the authoritative schema design for SŌSH Phase 1. It defines:

- Nine tables with full column lists, types, defaults, and constraints.
- RLS policies and the helper function used to scope every query to the authenticated user's businesses.
- Supabase Vault usage for all OAuth tokens (no raw tokens in any application table).
- Indexes for the hot query paths (publishing queue, dashboards, engagement inbox, AI cost reporting).
- Soft-delete strategy.
- A reusable `set_updated_at()` trigger and a single trial-clock-start trigger.
- The exact migration order to satisfy foreign-key dependencies.

This document is design-only. SQL migration files are produced in a follow-up session against this design.

---

## Conventions

- **Primary keys:** `uuid` generated by `gen_random_uuid()`.
- **Timestamps:** every table has `created_at timestamptz NOT NULL DEFAULT now()`. Tables that mutate also have `updated_at timestamptz NOT NULL DEFAULT now()` maintained by the shared `set_updated_at()` trigger.
- **Time semantics:** all timestamps stored UTC. Display localisation is done in the app via `date-fns` and the business `timezone`.
- **Enumerations:** Postgres `CHECK` constraints on `text` columns paired with TypeScript union types in `/lib/db/`. No Postgres `enum` types — they migrate poorly.
- **Foreign keys:** `ON DELETE` behaviour is stated per relationship below. Default is `RESTRICT`; `CASCADE` is used only where deletion of the parent logically erases the child.
- **Naming:** snake_case columns, plural snake_case tables, `*_id` for FKs.
- **Denormalisation:** `business_id` is denormalised onto every customer-data table that has a transitive parent (e.g. `posts`, `post_metrics`). This makes RLS policies single-join and dramatically cheaper on read.
- **Service role:** writes to `ai_usage` and `trial_state` are restricted to the Supabase service-role client (used by `/lib/ai/` and the billing/onboarding worker). User clients can only read.

## A. Identity & tenancy model

We use Supabase `auth.users` directly. Application-level user data is in a separate `profiles` table (created in a later migration if needed; not required for Phase 1's data model below).

**`businesses.owner_id`** is the canonical link from auth user → business. Phase 1 enforces "one business per user" in app code; the schema permits more.

The RLS helper function returns the set of business IDs the calling user can access. In Phase 1 access = ownership; in later phases the same function will resolve via a `business_members` join table without changes to any policy.

```sql
-- Helper: returns the business IDs the calling user can access.
-- Phase 1 implementation: ownership only.
CREATE OR REPLACE FUNCTION public.get_user_business_ids()
RETURNS uuid[]
LANGUAGE sql
STABLE
SECURITY DEFINER
SET search_path = public
AS $$
  SELECT COALESCE(array_agg(id), ARRAY[]::uuid[])
  FROM public.businesses
  WHERE owner_id = auth.uid()
    AND deleted_at IS NULL;
$$;

REVOKE ALL ON FUNCTION public.get_user_business_ids() FROM public;
GRANT EXECUTE ON FUNCTION public.get_user_business_ids() TO authenticated;
```

Notes:

- `STABLE` lets Postgres cache the result within a single statement, so a query touching multiple RLS-protected tables only resolves the user's businesses once.
- `SECURITY DEFINER` is required because the function reads from `businesses`, which itself has RLS — without `DEFINER` the function would recurse into its own policy.
- `SET search_path = public` is the standard hardening to prevent search-path injection on `SECURITY DEFINER` functions.
- The `auth.uid() IS NULL` case naturally returns an empty array; every policy that uses this function will deny by default for unauthenticated requests.

### 5. `posts`

The publishable unit. **Flat shape**: one row per (campaign, platform). The `business_id` is denormalised for RLS.

| Column | Type | Constraints / default |
|---|---|---|
| `id` | uuid | PK, default `gen_random_uuid()` |
| `campaign_id` | uuid | NOT NULL, FK → `campaigns.id` ON DELETE CASCADE |
| `business_id` | uuid | NOT NULL, FK → `businesses.id` ON DELETE CASCADE |
| `platform` | text | NOT NULL, CHECK in the platform set |
| `content` | text | NOT NULL |
| `hashtags` | text[] | NOT NULL, default `'{}'` |
| `media_urls` | text[] | NOT NULL, default `'{}'` |
| `scheduled_at` | timestamptz | NOT NULL |
| `published_at` | timestamptz | nullable |
| `platform_post_id` | text | nullable |
| `status` | text | NOT NULL, CHECK in `('draft','approved','scheduled','published','failed','skipped')`, default `'draft'` |
| `rejection_note` | text | nullable |
| `ai_generation_metadata` | jsonb | NOT NULL, default `'{}'` |
| `deleted_at` | timestamptz | nullable |
| `created_at` | timestamptz | NOT NULL, default `now()` |
| `updated_at` | timestamptz | NOT NULL, default `now()` |

**Status machine** (enforced in `/lib/db/posts.ts`, not by triggers):

```
draft ──► approved ──► scheduled ──► published
   │                            ↘
   └──► skipped                   failed (re-queue back to scheduled)
```

`rejection_note` is required (in app code) when transitioning to `skipped`.

**Indexes**

- `(status, scheduled_at) WHERE status = 'approved'` — partial index used by the publishing worker to find what's due. Specifically used as: `WHERE status = 'approved' AND scheduled_at <= now()`.
- `(campaign_id)` — campaign detail views.
- `(business_id, created_at DESC)` — dashboard activity feeds.
- `(business_id, status)` — dashboard filters.

**Notes**

- `business_id` is denormalised for RLS efficiency. Application code (`/lib/db/posts.ts`) is the only writer and must keep it consistent with the parent campaign.
- `ai_generation_metadata` is the only place we record per-post AI provenance: model, prompt id/version, brand voice snapshot, retry chain, raw input/output token counts. Aggregate cost reporting comes from `ai_usage` (table 9), not from this jsonb.
- Soft delete: published posts have legal / audit value; campaigns deletion cascades hard, but a single post deletion uses `deleted_at`.

### 6. `post_metrics`

Latest-known platform metrics for a post. **One row per post**, updated in place by the metrics worker; historical snapshots are out of scope for Phase 1 (a future `post_metrics_history` table can be added without schema churn).

|---|---|---|

| `post_id` | uuid | NOT NULL, UNIQUE, FK → `posts.id` ON DELETE CASCADE |
| `business_id` | uuid | NOT NULL, FK → `businesses.id` ON DELETE CASCADE |
| `likes` | int | nullable |
| `comments` | int | nullable |
| `shares` | int | nullable |
| `saves` | int | nullable |
| `clicks` | int | nullable |
| `reach` | int | nullable |
| `impressions` | int | nullable |
| `last_synced_at` | timestamptz | NOT NULL, default `now()` |
| `created_at` | timestamptz | NOT NULL, default `now()` |
| `updated_at` | timestamptz | NOT NULL, default `now()` |

**Indexes**

- `business_id`.
- `last_synced_at` — used by the metrics worker to find stale rows.

**Notes**

- **Nullable means "platform doesn't expose this metric."** Zero is a real value (a post with no likes); `NULL` is missing data. The UI must distinguish.

## C. Row Level Security

### Enablement

All nine tables enable RLS:

```sql
ALTER TABLE businesses        ENABLE ROW LEVEL SECURITY;
ALTER TABLE brand_voices      ENABLE ROW LEVEL SECURITY;
ALTER TABLE social_accounts   ENABLE ROW LEVEL SECURITY;
ALTER TABLE campaigns         ENABLE ROW LEVEL SECURITY;
ALTER TABLE posts             ENABLE ROW LEVEL SECURITY;
ALTER TABLE post_metrics      ENABLE ROW LEVEL SECURITY;
ALTER TABLE engagement_inbox  ENABLE ROW LEVEL SECURITY;
ALTER TABLE trial_state       ENABLE ROW LEVEL SECURITY;
ALTER TABLE ai_usage          ENABLE ROW LEVEL SECURITY;
```

### Standard policy pattern

Eight of the nine customer-data tables use the same policy pattern. `businesses` is the one exception (uses `owner_id` directly).

**For tables with `business_id` (everything except `businesses`):**

```sql
-- SELECT
CREATE POLICY "<table>_select_own" ON <table>
  FOR SELECT TO authenticated
  USING (business_id = ANY (get_user_business_ids()));

-- INSERT
CREATE POLICY "<table>_insert_own" ON <table>
  FOR INSERT TO authenticated
  WITH CHECK (business_id = ANY (get_user_business_ids()));

-- UPDATE
CREATE POLICY "<table>_update_own" ON <table>
  FOR UPDATE TO authenticated
  USING (business_id = ANY (get_user_business_ids()))
  WITH CHECK (business_id = ANY (get_user_business_ids()));

-- DELETE
CREATE POLICY "<table>_delete_own" ON <table>
  FOR DELETE TO authenticated
  USING (business_id = ANY (get_user_business_ids()));
```

The `WITH CHECK` clause on UPDATE is critical: without it, a user could `UPDATE posts SET business_id = '<other-business>'` and tunnel rows into another tenant's namespace. Both `USING` and `WITH CHECK` must reference the helper.

**For `businesses`:**

```sql
CREATE POLICY "businesses_select_own" ON businesses
  FOR SELECT TO authenticated USING (owner_id = auth.uid() AND deleted_at IS NULL);

CREATE POLICY "businesses_insert_own" ON businesses
  FOR INSERT TO authenticated WITH CHECK (owner_id = auth.uid());

CREATE POLICY "businesses_update_own" ON businesses
  FOR UPDATE TO authenticated
  USING (owner_id = auth.uid()) WITH CHECK (owner_id = auth.uid());

-- No DELETE policy: businesses are deleted by service-role only
-- (cascade implications and Stripe coordination required).
```

### Service-role-only writes

`ai_usage` and `trial_state` allow SELECT to the owner but restrict mutations to service role:

```sql
-- ai_usage
CREATE POLICY "ai_usage_select_own" ON ai_usage
  FOR SELECT TO authenticated
  USING (business_id = ANY (get_user_business_ids()));
-- No INSERT/UPDATE/DELETE policies for `authenticated`. Service role bypasses RLS.

-- trial_state
CREATE POLICY "trial_state_select_own" ON trial_state
  FOR SELECT TO authenticated
  USING (business_id = ANY (get_user_business_ids()));
-- No INSERT/UPDATE/DELETE policies for `authenticated`.
```

This is enforced by **omission**: with RLS enabled and no policy for a given action, that action is denied for all roles except those that bypass RLS (i.e. `service_role` and the table owner).

### Cross-tenant leakage checklist

Each policy was reviewed against these failure modes:

1. **`UPDATE … SET business_id = '<other>'`** — blocked by `WITH CHECK` on every UPDATE policy.
2. **Insertion into a foreign business** — blocked by `WITH CHECK` on every INSERT policy.
3. **Joins through unprotected tables** — every customer table has its own policy; there is no path that selects from one tenant via a join through another. The denormalised `business_id` columns mean we never traverse FKs in policy evaluation.
4. **Service-role leakage to client code** — the service-role client is only constructed in `/lib/supabase/server.ts` and only used by `/lib/ai/`, the Stripe webhook, the publishing worker, and the metrics worker. No request handler in `/app/(dashboard)` may import it.
5. **Anonymous access** — every policy is `TO authenticated`; the `anon` role can read nothing.
6. **Helper recursion** — `get_user_business_ids()` is `SECURITY DEFINER` so its query against `businesses` is not subject to the table's RLS.
7. **Realtime subscriptions** — when Supabase Realtime is enabled, RLS policies on the underlying table apply to subscriptions. No additional policies needed.

## D. Supabase Vault for token storage

OAuth tokens never appear in any application table. They live in `vault.secrets`, encrypted at rest, and are referenced from `social_accounts` only by their secret ID.

### Naming convention

Each secret is named:

```
sosh_token_{social_account_id}_{type}
```

where `{type}` ∈ `access` | `refresh`. Example: `sosh_token_b1f2…_access`.

This convention makes orphan-secret cleanup straightforward (a periodic job can list `vault.secrets` whose name prefix doesn't match a current `social_accounts.id`).

### Lifecycle

#### Creating a secret on connection

When `/lib/social/` completes the OAuth flow for a platform:

```sql
-- Inside a transaction, called from a SECURITY DEFINER function
-- in /lib/db/social-accounts.ts via the service-role client.

SELECT vault.create_secret(
  new_secret      => $1,                                 -- the raw access token
  new_name        => 'sosh_token_' || $2 || '_access',   -- unique per account
  new_description => 'SOSH access token for social_account ' || $2
) AS access_secret_id;
```

The returned `uuid` is stored in `social_accounts.vault_access_token_id`. The same flow is repeated for the refresh token if the platform issues one.

#### Reading a secret

```sql
SELECT decrypted_secret
FROM vault.decrypted_secrets
WHERE id = $1;  -- the vault secret ID from social_accounts
```

`vault.decrypted_secrets` is a view that decrypts on read. It is only readable by `service_role` (and the database superuser); it is not exposed via PostgREST. `/lib/social/` uses the service-role client to read it.

#### Refreshing a token in place

When a refresh response arrives, **update the existing secret** rather than creating a new one. The application then bumps `token_expires_at` on `social_accounts`.

```sql
SELECT vault.update_secret(
  secret_id  => $1,         -- existing vault secret ID
  new_secret => $2,         -- newly refreshed token
  new_name   => NULL,       -- keep name
  new_description => NULL   -- keep description
);
```

Updating in place keeps the FK in `social_accounts` stable and avoids an interim period where two secrets exist.

#### Revocation / disconnect

When the user disconnects an account, the application:

1. Sets `social_accounts.is_active = false`.
2. Calls `vault.delete_secret(secret_id)` for both access and refresh secrets.
3. Nulls the `vault_*_token_id` columns.

### Why this satisfies CLAUDE.md

`CLAUDE.md` requires that "no code outside `/lib/social/` ever calls Postiz directly" and that "no code outside `/lib/social/` ever knows that Postiz exists." With Vault-stored tokens, the `/lib/social/` layer becomes the sole holder of platform credentials. The rest of the codebase sees only `social_accounts` rows with opaque vault IDs and cannot decrypt anything because vault read access is gated by service role, which the dashboard runtime does not have.

If, in a later phase, a platform-specific provider replaces Postiz for that platform, the same `social_accounts` row (and its vault secrets) is reused — only the implementation in `/lib/social/<platform>/` changes.

## F. Triggers

### `set_updated_at()` — shared

```sql
CREATE OR REPLACE FUNCTION public.set_updated_at()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$;

REVOKE ALL ON FUNCTION public.set_updated_at() FROM public;
```

Applied to every table that has `updated_at`:

```sql
CREATE TRIGGER trg_<table>_updated_at
BEFORE UPDATE ON <table>
FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();
```

Tables: `businesses`, `brand_voices`, `social_accounts`, `campaigns`, `posts`, `post_metrics`, `engagement_inbox`, `trial_state`. (`ai_usage` has no `updated_at`.)

### Trial-clock-start trigger on `social_accounts`

The 14-day trial clock begins when the user connects their first social account. This is a hard product rule (`CLAUDE.md` strategic decisions) so we enforce it in the database, not just in app code.

```sql
CREATE OR REPLACE FUNCTION public.start_trial_on_first_social_account()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_existing_count int;
BEGIN
  -- Only act on the first active social_account for this business.
  SELECT count(*) INTO v_existing_count
  FROM social_accounts
  WHERE business_id = NEW.business_id
    AND id <> NEW.id;

  IF v_existing_count = 0 THEN
    UPDATE trial_state
    SET trial_started_at = now()
    WHERE business_id = NEW.business_id
      AND trial_started_at IS NULL;
  END IF;

  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_social_accounts_start_trial
AFTER INSERT ON social_accounts
FOR EACH ROW EXECUTE FUNCTION public.start_trial_on_first_social_account();

REVOKE ALL ON FUNCTION public.start_trial_on_first_social_account() FROM public;
```

**Rationale for using a trigger here (despite preferring app-level enforcement elsewhere):** the trial clock is a billing-relevant fact. If a future code path forgets to update `trial_state`, the user gets a free trial extension. Putting it in the database makes it impossible to bypass.

`SECURITY DEFINER` is required because authenticated users do not have INSERT/UPDATE rights on `trial_state`; the trigger runs as the function owner (typically `postgres`) and writes regardless.

The condition `trial_started_at IS NULL` makes the update idempotent: if the trigger fires twice for some reason (e.g. a row deleted and re-inserted), the clock does not restart.

## G. Soft deletes

Tables with `deleted_at`:

| Table | Reason |
|---|---|
| `businesses` | Subscription / tax / Stripe coordination requires retention. Hard delete only after Stripe customer is fully closed. |
| `campaigns` | Campaigns reference `posts` that may be billing-relevant; hiding rather than removing preserves history. |
| `posts` | Published posts on real social platforms cannot be "undeleted" by the platform; we keep our record so users can see what was published even after they archive a campaign. |

Tables **without** `deleted_at` (hard delete only):

| Table | Reason |
|---|---|
| `brand_voices` | 1:1 with business; cascades on business delete. No independent lifecycle. |
| `social_accounts` | We use `is_active = false` for the "soft" state (revoked / disconnected). True deletion removes the vault secrets and is a real action. |
| `post_metrics` | Pure derivative data; cascades with `posts`. |
| `engagement_inbox` | High-volume, primarily transient. `status = 'ignored'` is the soft state. Cascade with business. |
| `trial_state` | 1:1 with business. |
| `ai_usage` | Append-only audit log; never deleted in normal operation. |

Soft-delete filtering (`WHERE deleted_at IS NULL`) is enforced in `/lib/db/` query helpers, not in RLS policies. Putting it in RLS would silently hide rows from operators investigating issues; keeping it in app code makes the filter visible and overridable for service work.

| 13 | `ai_usage` | FK → `businesses`. |

A small companion trigger on `businesses` INSERT creates a `trial_state` row automatically, so the app never has to remember:

```sql
CREATE OR REPLACE FUNCTION public.create_trial_state_for_new_business()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  INSERT INTO trial_state (business_id) VALUES (NEW.id)
  ON CONFLICT (business_id) DO NOTHING;
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_businesses_create_trial_state
AFTER INSERT ON businesses
FOR EACH ROW EXECUTE FUNCTION public.create_trial_state_for_new_business();

REVOKE ALL ON FUNCTION public.create_trial_state_for_new_business() FROM public;
```

This trigger is included in the `trial_state` migration (step 7), since it belongs to that table's lifecycle.

## I. Trade-offs and deferrals

- **Engagement inbox is in Phase 1.** Earlier draft deferred it; this revision includes it because the Pro plan advertises an "engagement inbox" and we don't want a feature flag in the schema.
- **Tokens via Vault, not Postiz-only.** `/lib/social/` now owns credentials directly. This gives us the option to talk to platform APIs without going through Postiz when we need to (metrics fetching, engagement ingestion). Postiz still fronts publishing per the `SocialProvider` rule.
- **Flat posts (no parent + variants).** Cross-platform "approve once → publish everywhere" must be implemented in app code by creating N rows in one transaction and updating their statuses together. The simpler shape is worth the slight loss of relational expressiveness.
- **`post_metrics` is upsert-in-place.** No historical snapshots in Phase 1. A separate `post_metrics_history` table will be added if/when the analytics product needs trends.
- **No brand voice versioning.** The `ai_generation_metadata` jsonb on `posts` carries enough provenance for Phase 1.
- **No `business_members` table yet.** "One business per user" is enforced in app code; the `get_user_business_ids()` helper resolves via `businesses.owner_id`. Phase 2 (or earlier, if needed) can add the join table and update the helper without touching any policy or table.
- **`'agency'` is in the `plan` CHECK** but no Phase 1 code path writes it — reserved for Phase 4 per `CLAUDE.md` strategic decisions.
- **`language` enum collapses `pt-PT`/`pt-BR` to `pt`.** Per-region targeting can be added later by widening the CHECK and migrating data.
